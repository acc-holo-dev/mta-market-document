# Модель домена

Термины не синонимы. Если в коде или UI они смешаны — это баг языка, чинить.

## Сущности

| Сущность | Смысл |
|---|---|
| User | Аккаунт площадки. Покупатель и продавец — роли одного пользователя. |
| Account | Внешний логин (`provider` + `providerAccountId`). Сейчас живой только Discord. |
| Resource | Карточка товара. Не файл. |
| ResourceVersion | Конкретный релиз: URL, размер, checksum. Скачивается версия. |
| Service | Услуга (в схеме есть, потока нет). |
| Discount | Скидка/промокод (хелперы есть, витрины нет). |
| Order | Корзина/заказ, снимок сумм. В схеме есть; основной путь покупки — `Purchase`. |
| Payment | Деньги у провайдера. Один платёж на заказ в целевой модели. |
| Purchase | Право на ресурс после оплаты. Snapshot цены и комиссии. |
| License | Право эксплуатации. Выдаётся из purchase. |
| Installation | Конкретная установка. Identity — ключ, не HWID. |
| PaymentProviderEvent | Идемпотентная запись вебхука. |
| SellerBalance / FinancialTransaction | Деньги продавца. Не путать с Payment. |

## Связи (цель)

```
User → Order → Payment
          ↓
     OrderItem → Purchase → License → Installation
```

Сейчас API часто создаёт `Purchase` напрямую (`POST /purchases`), минуя полноценный checkout заказа.

## Инварианты

1. Успешный платёж не создаёт вторую покупку на тот же объект (идемпотентность).
2. Snapshot покупки не переписывается после COMPLETED.
3. Отзыв лицензии гасит её installation.
4. Сумма проводок должна сходиться с балансом (сейчас это не гарантировано транзакцией БД).
5. Активировать лицензию может только `purchase.buyerId`.

## Не MVP

Подписки, биржа заказов, бандлы как отдельный продукт.
