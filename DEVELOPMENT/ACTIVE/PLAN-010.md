=================================================
0. ЦЕЛЬ PLAN-010
   ==================================================

Переход состояния:

ИЗ:

Создатель видит единственный сигнал о спросе — завершённые продажи.
Просмотры карточек не измеряются вообще: IDEAS §4 («Seller analytics уровня
ecommerce: просмотры → конверсия») пуст, CREATOR Loop (§9: Sales → Update →
Return) не даёт создателю понять, есть ли интерес до покупки.

В:

Каждое открытие страницы ресурса считается (честная page-view метрика);
создатель видит в своём магазине: просмотры за 30 дней (всего и по
ресурсам), конверсию просмотр→покупка. Только свои данные; без идентичностей
зрителей (агрегат-таблица, публичных метрик просмотров нет).

После PLAN-010 создатель отвечает на вопрос:

"Мой ресурс смотрят? Сколько смотревших покупают?"

— и принимает решения (обложка, описание, цена) на реальных данных.

=================================================
1. СТРАТЕГИЧЕСКАЯ ИДЕЯ
   ==================================================

План не называется:

"Analytics platform".

Суть — дать создателю минимальный честный сигнал спроса:

"Просмотры — это интерес. Покупки — это доверие. Конверсия их связывает."

Никаких сессий, воронок, гео, A/B — одна метрика (просмотры карточек) и
одна производная (конверсия). Всё остальное — будущие фазы из IDEAS §4.

=================================================
2. ПРИНЦИПЫ
   ==================================================

1. **Privacy**: не хранить идентичности зрителей. Только агрегат
   (ресурс × день × счётчик). Зрители — не пользователи в этой модели.
2. **Honesty** (Vision Principle 5): views = открытия страницы ресурса
   (page views), никаких inflate-хаков и никакого «примерного» подсчёта.
   Показывать продавцу именно открытия.
3. **Public metrics unchanged**: просмотры НЕ показываются покупателям
   (VISION §20: публичные агрегаты — только те, что разрешает бизнес-логика;
   публичность просмотров — решение будущей фазы).
4. **Real data only**: счётчик растёт только от реальных открытий страницы.

=================================================
3. WORKSTREAM A — МОДЕЛЬ
   ======================

A-001 — ResourceViewDaily

- resourceId (FK Resource, Cascade);
- day (дата, YYYY-MM-DD, MSK/UTC — UTC);
- views (Int);
- unique [resourceId, day]; индекс по resourceId.
Upsert-инкремент при открытии страницы. Никаких идентичностей, сессий,
cookie — это принципиальное решение (анонимно и дёшево).

---

A-002 — Границы

- Открытие страницы ресурса = GET /resources/:slug из web → отдельный
  публичный POST /resources/:slug/view с фронтенда (once per mount);
  GET остаётся чистым read (никаких side effects на чтение).
- Rate limit стандартный; валидация PUBLISHED.

=================================================
4. WORKSTREAM B — API
   ===================

B-001 — POST /resources/:slug/view

- публичный (гость считается так же);
- 404 для не-PUBLISHED;
- upsert инкремента (resourceId × today);
- без тела, без параметров, идемпотентность не требуется (честные page
  views: каждый mount = просмотр).

---

B-002 — Аналитика продавца

GET /seller/analytics (auth, seller):

- days=30 (фиксированный горизонт, константа);
- totalViews (сумма по всем своим ресурсам за 30д);
- byResource: [{ resourceId, slug, title, views30d, purchases30d,
  conversionPct }] — конверсия = завершённые покупки ресурса за 30д /
  просмотры × 100 (округление до целых; views=0 → conversion null);
- только свои ресурсы (PUBLISHED + все статусы? — аналитика по всем своим,
  включая черновики? Просмотры бывают только у PUBLISHED; по черновикам
  строки не показывать).

=================================================
5. WORKSTREAM C — ПОВЕРХНОСТИ
   ===========================

C-001 — Fire-and-forget просмотр

Страница ресурса: useEffect (once per mount) → POST /resources/:slug/view
(только если resource PUBLISHED). Не блокирует рендер, ошибки молча.

---

C-002 — Магазин: вкладка/блок «Аналитика»

/store (или /seller — где живёт кабинет): блок «Аналитика (30 дней)»:

- всего просмотров;
- конверсия средняя;
- таблица по ресурсам: просмотры / покупки / конверсия.

Empty state: «Пока нет просмотров».

=================================================
6. WORKSTREAM D — PERFORMANCE
   ===========================

- upsert по unique-индексу (одна запись на ресурс×день) — O(1);
- аналитика — один bounded-запрос агрегата по своим ресурсам;
- публичные поверхности не изменены (Home/activity не трогаем).

=================================================
7. WORKSTREAM E — SEED
   ====================

seed-plan005: заполнить ResourceViewDaily за последние 30 дней
(правдоподобные объёмы для demo-ресурсов, нули для новых) — чтобы блок
аналитики был живым сразу.

=================================================
8. TESTING — API
   ==============

- view: 201/200 для PUBLISHED; 404 для DRAFT/SUSPENDED; счётчик растёт
  ровно на 1 за вызов; отдельные дни дают отдельные строки;
- analytics: только свои ресурсы; чужие не видны; конверсия считается
  (создать покупку → проверить); views=0 → conversion null;
- без auth → 401; не-продавец → пустой набор (не 403? — решить: пусто).

   ===================

SCENARIO 1 — СОЗДАТЕЛЬ: публикует ресурс → читатель открывает карточку →

=================================================
14. НЕ ДЕЛАТЬ
   ==========

- Идентичности зрителей, сессии, cookie-трекинг, гео;
- публичные показы просмотров (решение будущей фазы);
- воронки/A/B/heatmaps/источники трафика (IDEAS §4 остаётся пулом идей);
- analytics для услуг/серверов (только ресурсы);
- изменения Home/activity/поиска.

=================================================
15. FINAL PRINCIPLE
   =================

Создатель без данных о спросе — работает вслепую.

Одна честная метрика (просмотры) и одна производная (конверсия) дают
создателю достаточно, чтобы принимать решения, — и ничего больше, чем
платформа имеет право знать.
